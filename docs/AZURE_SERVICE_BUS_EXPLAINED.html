Azure Service Bus, Explained

A from-first-principles guide to Azure Service Bus — what a message broker is, why asynchronous messaging matters, and how queues, topics, subscriptions, peek-lock, retries and dead-letter queues fit together — with plain-language analogies and interactive animations you can play. Then, exactly how Service Bus is wired into this event-ticketing platform (catalog / booking / identity microservices).

Part 1 What is a message broker & why go async?

A message broker is a piece of infrastructure that sits between the programs that produce information and the programs that consume it. Instead of one service calling another directly and waiting for a reply, the producer drops a message into the broker and moves on. The broker holds it safely until a consumer is ready to pick it up.

📮
Analogy — the postal system vs. handing over a letter in person. A synchronous HTTP call is like walking to your neighbour's house and standing there until they read your note and answer. If they're out, you're stuck. A broker is the postal system: you drop the letter in a postbox (produce), the sorting depot holds and routes it (broker), and the recipient reads it whenever they open their mailbox (consume). Neither of you has to be available at the same instant.

That single shift — from "call and wait" to "send and forget" — buys three things that matter enormously in a microservices system like this ticketing platform:

🔗 Decoupling

Producer and consumer never need to know each other's address, be online together, or agree on speed. Catalog can publish an event even if booking is mid-deploy.

🛡️ Resilience

If a consumer crashes, messages wait in the broker instead of being lost. When it recovers, it drains the backlog. A slow subscriber can't take down the publisher.

⚖️ Load-leveling

A traffic spike (a big concert on-sale) fills the queue, and consumers work through it at their own steady rate — the broker absorbs the burst like a shock-absorber.

Azure Service Bus is Microsoft's fully-managed enterprise message broker (a cloud SaaS). It is the "sorting depot" this platform uses for events that travel between microservices.

The namespace — the post office building

Everything in Service Bus lives inside a namespace: a named container with its own address, security boundary and capacity. It's the top-level thing you create in Azure.

🏤
Analogy. The namespace is the post office building at a specific street address (e.g. sb-myticketzm.servicebus.windows.net). Inside it are counters (queues) and broadcast boards (topics). You get keys to the building, and everything inside shares its walls, staff and opening hours.

Queues vs. Topics + Subscriptions

Service Bus offers two delivery shapes. Knowing when to reach for each is the single most important concept.

Queue — point-to-point, competing consumers

A queue holds messages that are delivered to exactly one consumer. If several worker instances read the same queue, each message goes to just one of them — they compete and share the load.

🧍‍♂️🧍‍♀️
Analogy. A queue is a single line at a bank counter. There may be three tellers, but each customer is served by exactly one teller. No two tellers handle the same customer.
Producer→ 📥 Queue→ Consumer A (one of these)

Topic + Subscriptions — publish/subscribe fan-out

A topic looks like a queue to the sender, but on the receiving side it fans out to one or more subscriptions. Every subscription gets its own copy of each message. Consumers read from a subscription, never the topic directly.

📻
Analogy. A topic is a radio broadcast. Each subscription is a listener's personal filtered mailbox / recording — everyone tuned in receives the same show, but each keeps their own copy to play back at their own pace. One event, many independent consumers.
Producer→ 📢 Topic ⇉ Subscription 1→Consumer X Subscription 2→Consumer Y
Rule of thumb: use a queue when exactly one worker should handle each message (a job to do once). Use a topic when several independent services each care about the same event. This platform uses topics so that (for example) a single "ticket purchased" event can eventually feed analytics, notifications and organizer dashboards independently.

Messages, properties & sessions (ordering)

A Service Bus message has two parts: a body (the actual payload — usually JSON) and a set of properties / headers (metadata such as content type, a message ID, a correlation ID, and custom application properties used for routing and filtering).

✉️
Analogy. Think of an envelope. The contents (letter) are the body; the writing on the envelope — recipient, return address, "FRAGILE", a tracking number — are the properties. The sorting depot routes on the envelope without opening the letter.

Sessions & partition keys — keeping order

Normally messages can be processed in parallel and may finish out of order. When order within a related group matters, you set a session ID (or partition key). All messages sharing that ID are delivered to one consumer, in order, one at a time.

🗂️
Analogy. A session is a clerk who keeps one customer's letters in a single labelled folder and reads them strictly in the order they arrived, while other clerks handle other customers in parallel. You get ordering per customer without serialising everyone.

Peek-Lock vs. Receive-and-Delete — settlement

How does the broker know a message was actually handled — and not lost when a consumer crashes halfway? Through settlement. There are two receive modes.

Receive-and-Delete simple, risky

The broker hands over the message and deletes it immediately. Fast, but if the consumer crashes before finishing, the message is gone forever. Fine for throwaway telemetry, dangerous for business events.

Peek-Lock safe, default

The broker gives the consumer the message but keeps a locked copy. The consumer must then settle it: complete (done — remove it), abandon (put it back for retry), or dead-letter (set aside as un-processable). If the lock expires with no settlement, the message reappears for another attempt.

📄
Analogy. Peek-lock is like taking a letter from the depot but the depot keeps a photocopy until you phone back to confirm "handled". If you never call (you crashed), they assume it wasn't done and hand the copy to someone else. That's why peek-lock gives at-least-once delivery.
Auto-complete OFF = manual settlement. With auto-complete on, the framework settles the message the instant your handler returns. With it off, your code decides when to complete — only after the work is truly persisted. This platform uses manual settlement (auto-complete: false) so a message is completed only after booking-service has finished writing to MongoDB.

Delivery guarantees, idempotency & duplicate detection

Peek-lock's safety comes with a trade-off you must design for.

GuaranteeWhat it meansConsequence
At-least-onceEvery message is delivered one or more times (Service Bus's default with peek-lock).Your consumer may see the same message twice — e.g. it processed successfully but crashed before completing.
IdempotencyYour handler produces the same result no matter how many times it runs for a given message.The correct defence against duplicates: key work by message ID and ignore repeats.
Duplicate detectionA namespace feature: the broker drops messages with a repeated MessageId inside a time window.Stops the producer from accidentally sending the same message twice.
🧾
Analogy. Idempotency is a shop that checks the receipt number before charging you again — if that receipt was already rung up, it does nothing rather than double-charging. In this platform, "initialise inventory for event X" must be safe to run twice.

Retry, max delivery count & the Dead-Letter Queue

What happens when a consumer keeps failing on the same message? You don't want it stuck in an infinite loop, blocking everything behind it.

Each redelivery increments a delivery count. Consumers typically retry with exponential backoff (wait 1s, then 2s, then 4s… giving a struggling downstream time to recover). Once the delivery count crosses max delivery count, the broker moves the message to the Dead-Letter Queue (DLQ) — a special sub-queue for "poison" messages that a human or a repair job can inspect later.

🗑️
Analogy. The DLQ is the post office's undeliverable-mail bin. After the carrier tries the address N times and always fails, they stop wasting trips and set the letter aside in the dead-letter office for investigation — the rest of the mail keeps flowing.
📢 Topic / Sub→ Consumer ⤳ fail ×N → 💀 Dead-Letter Queue
In this platform: consumers retry 3 times with backoff 1s → 10s (multiplier 2.0). After the attempts are exhausted, the message dead-letters instead of blocking the subscription. You'll see this animated in Part 2.

Retention, TTL, quotas & offline consumers — and where each is configured

What happens to a message between being published and being processed: where it lives, how long it waits, what happens if no consumer is listening — and, importantly, which knob is set where. Service Bus splits configuration into two layers, and mixing them up is the number-one source of surprises.

How messages are kept

Every message is written to durable, replicated storage before the broker acknowledges the send — it survives broker restarts and is never held only in the producer's or consumer's memory. On a topic, each subscription keeps its own independent copy, so a slow or offline consumer on one subscription never affects another. A message stays put until it is completed, expires (TTL), or is dead-lettered.

📪
Analogy. A subscription is a mailbox. A letter stays in the box until you take it out (complete), it passes its use-by date (TTL), or the post office moves it to the undeliverable bin (dead-letter). It does not vanish just because you're away.

Two layers of configuration (the key idea)

Service Bus exposes these behaviours as entity properties on the queue/topic/subscription — set when the entity is provisioned, not in your app code. Your app's application.yml only tunes how the client talks to the entity.

LayerSet whereControlsExamples
Broker-side entity properties retention On the queue / topic / subscription, at provisioning — Portal, az CLI, Terraform, or the Admin SDK (locally: the emulator's config.json) How long & how messages are retained — TTL, lock, delivery cap, dead-lettering, size quota, dedup, sessions DefaultMessageTimeToLive LockDuration MaxDeliveryCount DeadLetteringOnMessageExpiration MaxSizeInMegabytes

Common trap: TTL/retention/redelivery are entity properties — you cannot change them from consumer code. To keep messages longer, change the topic/subscription at provisioning, not application.yml.

Time-to-live (TTL) — how long a message is kept

  • Every queue/subscription has a DefaultMessageTimeToLive — an ISO-8601 duration (e.g. PT1H = 1 hour, P14D = 14 days). Azure's own default is 14 days (also the max on Standard; Premium can hold longer).
  • A publisher may set a shorter TTL per message (Message.TimeToLive); the effective TTL is the smaller of the message's and the entity's.
  • When TTL elapses before the message is consumed, it expires. If DeadLetteringOnMessageExpiration = true it moves to the Dead-Letter Queue (recoverable); otherwise it is silently dropped.
In this project (dev emulator): TTL is deliberately short — DefaultMessageTimeToLive = PT1H on every topic and subscription, with DeadLetteringOnMessageExpiration = true. So a message left unconsumed for > 1 hour is dead-lettered (not lost). In production you'd raise this at provisioning (e.g. P3D).

Lock, redelivery & dead-lettering — the lifecycle rules

Active→ 🔒 Lockedpeek-lock→ ✓ Completeremoved
  • Delivered under peek-lock → the message is Locked (invisible to others) for LockDuration. Azure default is 30 s, max 5 min.
  • Consumer completes → removed. Consumer abandons, crashes, or the lock expires → back to Active and the delivery count +1.
  • Long handlers can auto-renew the lock beyond LockDuration (up to max-auto-lock-renew-duration) so they aren't cut off mid-work.
  • Once delivery count > MaxDeliveryCount (Azure default 10) the message is dead-lettered. Expired-by-TTL messages dead-letter too. The DLQ is a real sub-queue you can read, inspect and replay.

Quotas & what happens when consumers are DOWN

If a consumer is offline, its messages simply accumulate in the subscription, durably and in order, and are processed when it returns — nothing is lost for being offline. Two limits apply while it's down:

LimitProperty / valueWhat happens
TTL expiryDefaultMessageTimeToLive (dev: 1 h)Backlog older than the TTL is dead-lettered — a long outage can DLQ a chunk of the backlog.
Entity size quotaMaxSizeInMegabytes — Standard 1–5 GB, Premium up to 100 GBWhen the subscription fills, the broker rejects new sends (QuotaExceeded / ServerBusy) — deliberate back-pressure that protects the system.
Auto-delete on idleAutoDeleteOnIdle (default: never)Not set here, so idle subscriptions are kept indefinitely.
On recovery: the consumer's prefetch-count and max-concurrent-calls let it drain the backlog quickly — in this app, 10 prefetched and 5 processed concurrently.

How the entity properties are actually set

These live on the entity, so you set them at provisioning. Same knobs, three surfaces:

# az CLI — create the subscription with retention rules
az servicebus topic subscription create -g rg-ticketing --namespace-name sb-myticketzm \
  --topic-name catalog-events --name booking-service \
  --default-message-time-to-live P3D \      # TTL = 3 days
  --lock-duration PT1M \                     # peek-lock window
  --max-delivery-count 10 \                  # then → DLQ
  --dead-lettering-on-message-expiration true

# Terraform (azurerm_servicebus_subscription)
default_message_ttl                  = "P3D"
lock_duration                        = "PT1M"
max_delivery_count                   = 10
dead_lettering_on_message_expiration = true

# Local emulator (docker-resources/servicebus/config.json) — same properties:
"Properties": { "DefaultMessageTimeToLive": "PT1H", "LockDuration": "PT1M",

When it recovers, because settlement is manual (auto-complete=false), each message is removed only after the handler succeeds; a crash mid-processing releases the lock after 1 min and redelivers, up to 3 times, then dead-letters. The app also retries 3× in-process (1s→10s) on each delivery before it abandons.

Subscription filters & rules

A subscription doesn't have to receive every message on its topic. Each subscription can carry rules — most commonly SQL filters that test message properties, e.g. eventType = 'EventPublished' AND region = 'ZM'.

📬
Analogy. A filter is a mailbox that only accepts letters matching a rule — "only bills addressed to Flat 3". The broadcast still goes out to everyone's mailbox, but each mailbox quietly discards what it doesn't care about, so its consumer only ever sees relevant mail.
Filters keep consumers simple and efficient: instead of one big consumer with a giant if/switch, you can have several narrowly-scoped subscriptions, each fed only the message types it handles.

Competing consumers & scaling out

When one consumer can't keep up, you run more instances of the same consumer reading the same queue or subscription. The broker load-balances messages across them — this is the competing consumers pattern, and it's how you scale throughput horizontally.

🏦
Analogy. Open more tellers on the same line. Customers (messages) are pulled by whichever teller is free. Double the tellers, roughly double the throughput — no code changes, just more instances. (See the live demo in Part 2.)
Ordering caveat: more competing consumers means messages can finish out of order. If you need order, use sessions — the broker pins each session to one consumer while still spreading different sessions across the pool.

Part 3 How this ticketing platform uses Service Bus

The Event Ticketing System is a set of Spring Boot microservices (catalog-service, booking-service, identity-service) using Netflix DGS for GraphQL and Spring Cloud Stream with the Azure Service Bus binder for messaging. It runs a deliberate two-tier event model.

Tier 1 — Intra-service Modulith + PostgreSQL

Events within a single service use Spring Modulith, persisted to a PostgreSQL event_publication table before the listener runs. This gives guaranteed local delivery and auto-republish on restart. It never touches Service Bus.

Tier 2 — Cross-service Cloud Stream → Service Bus

Events between services travel over Spring Cloud Stream → Azure Service Bus topics. This is where namespaces, topics, subscriptions, peek-lock, retry and DLQ from Part 1 all apply.

Why the split? Modulith needs a blocking JDBC driver for its guaranteed local outbox, but the services are reactive (MongoDB). Rather than compromise, in-process events use the reliable PostgreSQL outbox, while anything crossing a service boundary rides the durable, fan-out-capable Service Bus. Right tool for each distance.

End-to-end scenarios

Scenario A — Organizer publishes a new event (fully wired) has consumer

This is the flow the Part 2 animation mirrors, using the real names.

  1. Organizer publishes an Event in catalog-service

    A Lusaka promoter creates and publishes "Afrobeats Live @ Heroes Stadium". catalog-service saves it (MongoDB) and calls StreamBridge.send("eventOutput-out-0", EventPublished), sending an EventPublished message to the catalog-events topic.

  2. The topic fans out to the booking-service subscription

    Service Bus places a copy of the message in the booking-service subscription's mailbox. It waits there durably — even if booking-service is momentarily down.

  3. booking-service receives under peek-lock

    catalogEventConsumer-in-0 picks up the message with a lock (the broker keeps a copy). It initialises ticket inventory and the escrow / commission ledger for the new event.

  4. Settle on success

    Because settlement is manual (auto-complete: false), booking-service completes the message only after inventory + escrow are persisted. The copy is removed from the subscription. ✅

  5. On failure — retry then dead-letter

    If processing throws (say the escrow write fails), the message is redelivered with exponential backoff: attempt 1 → wait ~1s → attempt 2 → wait ~2s → attempt 3. After 3 failed attempts the message is moved to the Dead-Letter Queue for catalog-events/booking-service, where it can be inspected and replayed — while the rest of the subscription keeps flowing.

Idempotency matters here: because delivery is at-least-once, "initialise inventory for event X" must be safe to run more than once — key it by the event ID so a duplicate delivery is a no-op.

Scenario B — Customer buys a ticket with mobile money producer only

  1. Customer pays via MTN / Airtel / Zamtel

    A buyer pays for a ticket through mobile money. booking-service confirms the payment, mints the ticket (with its QR code for venue validation), and updates escrow/commission.

  2. booking-service emits TicketPurchased

    It calls StreamBridge.send("ticketOutput-out-0", TicketPurchased), publishing a TicketPurchased message to the booking-events topic — intended for downstream consumers such as analytics and notifications (e.g. a WhatsApp "here's your ticket" message).

  3. No in-repo subscriber yet — extension point

    Called out honestly: the booking-events topic has only a default subscription and no consumer in this repository today. Messages are retained but not yet processed. Adding an analytics or notification service is a drop-in: create a subscription and a *Consumer-in-0 binding — no producer changes needed. This is exactly the pub/sub decoupling benefit from Part 1: the producer already does the right thing; consumers can be added later without touching it.

Dev → Prod swap (no code changes)

The same binder configuration runs against a local emulator in dev and a real, credential-free namespace in production — the only difference is the active Spring profile.

Local dev — local profile

  • Official Azure Service Bus emulator in Docker (Colima / arm64)
  • Backed by Azure SQL Edge (arm64-native store)
  • Injects the emulator connection string with UseDevelopmentEmulator=true
  • Topics/subscriptions pre-declared in the emulator config

Production — prod profile

  • Microsoft Entra managed identity — no SAS keys
  • Secrets pulled from Key Vault
  • Least-privilege RBAC: Azure Service Bus Data Sender + Data Receiver
  • Real namespace, Standard/Premium tier
# The entire swap — no code, no rebuild:
export SPRING_PROFILES_ACTIVE=prod
# prod profile -> managed identity + Key Vault + real namespace
# dev default  -> local profile -> emulator on 5673, UseDevelopmentEmulator=true
Why this is clean: the application never hardcodes credentials. Dev uses a keyless emulator flag; prod uses keyless managed identity. Flipping one environment variable moves between them.
