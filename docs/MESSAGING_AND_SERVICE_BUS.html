Messaging Architecture & Azure Service Bus Configuration

How cross-service events flow in the Event Ticketing platform, the exact state of Azure Service Bus vs RabbitMQ in this codebase, why each exists, and a step-by-step guide to configuring Service Bus for real Azure, a local emulator, or a RabbitMQ fallback.

✅❌ Are Azure Service Bus and RabbitMQ both configured?

Short answer: no. Only Azure Service Bus is wired into the application code (via Spring Cloud Stream), but it has no working credentials locally so it isn't operational. RabbitMQ runs as a container but no backend service connects to it — it is orphaned infrastructure for the ticketing system.

🎯 Why we need each broker

Azure Service Bus intended broker

The platform's designed cross-service event bus (topics catalog-events, booking-events, identity-events). Chosen for enterprise-grade delivery:

  • Topics & subscriptions — pub/sub fan-out (multiple services consume one event)
  • Dead-letter queues + exponential retry (already tuned: 3 retries, 1s→30s)
  • Managed identity + Key Vault — credential-free auth in Azure
  • Sessions / ordering, duplicate detection, at-least-once delivery
  • Fully managed SaaS — no broker to operate in production

RabbitMQ currently unused

In the ticketing system it serves no purpose today — nothing binds to it. It exists in the shared docker-resources stack (labelled “shared message broker”). Its realistic roles:

  • Local-dev alternative to Service Bus — run offline without an Azure namespace (needs the RabbitMQ binder added — see Option C)
  • Shared infra for a sibling project (e.g. twende-ride) in the same folder
  • Candidate for future queue/worker workloads

Decision needed: either wire it as the local binder, or drop it from the ticketing stack to avoid confusion.

🏛️ Event architecture review

The platform uses a deliberate two-tier event model. Understanding it explains why Service Bus matters and where it fits.

Tier 1 — Intra-service working

Events within one service use Spring Modulith + PostgreSQL (event_publication table). Guaranteed delivery, auto-republish on restart. Verified healthy at boot: “No publication found”, Hikari pool up. Independent of Service Bus.

Tier 2 — Cross-service blocked

Events between services use Spring Cloud Stream → Azure Service Bus (StreamBridge.send() and function bindings). This is the tier currently non-functional locally because Service Bus has no credentials.

Cross-service event flow (as coded)

   CATALOG SERVICE            IDENTITY SERVICE                 BOOKING SERVICE
   (event owner)             (user/org owner)              (ticket/payment owner)
        │                          │                                │
        │ eventOutput-out-0        │ userOutput-out-0               │ ticketOutput-out-0
        │ userRoleOutput / org     │ organizationOutput            │ chargeback / notification / org
        ▼                          ▼                                ▼
  ┌───────────────┐         ┌────────────────┐              ┌────────────────┐
  │ catalog-events│         │ identity-events│              │ booking-events │   ◄─ Azure Service Bus TOPICS
  └───────┬───────┘         └────────────────┘              └────────────────┘
          │
          │  subscription: "booking-service"  (consumer group)
          ▼
  ┌───────────────────────────┐
  │ BOOKING SERVICE           │   catalogEventConsumer-in-0
  │ catalogEventConsumer      │   (max-attempts 3, backoff 1s→10s ×2.0)
  └───────────────────────────┘

  Binder: servicebus (default)   Entity type: TOPIC   Settlement: manual (auto-complete=false, checkpoint=RECORD)
Producers publish imperatively via StreamBridge.send("<binding>-out-0", event); the only declared consumer today is booking-service listening on catalog-events. Other topics (booking-events, identity-events) are produced but have no in-repo subscriber yet.

☁️ Option A — Configure a real Azure Service Bus namespace

Production / staging path. Requires an Azure subscription. Standard tier or higher — the Basic tier has no topics, and this system uses topics.

  1. Provision the namespace & topics (Azure CLI)

    Standard tier gives topics + subscriptions. Create one namespace and the three core topics.

    # login + resource group
az login
az group create --name rg-ticketing --location southafricanorth

# namespace (name must be 6–50 chars, globally unique)
az servicebus namespace create \
  --resource-group rg-ticketing \
  --name sb-myticketzm-dev \
  --sku Standard

# topics
for t in catalog-events booking-events identity-events; do
  az servicebus topic create -g rg-ticketing \
     --namespace-name sb-myticketzm-dev --name $t
done

# subscription: booking-service consumes catalog-events (group = subscription name)
az servicebus topic subscription create -g rg-ticketing \
  --namespace-name sb-myticketzm-dev \
  --topic-name catalog-events --name booking-service

  2. Choose an authentication method

    (a) Connection string — simplest for dev. (b) Managed identity + RBAC — recommended for anything running in Azure (no secrets).

    # (a) SAS connection string (dev / quick start)
az servicebus namespace authorization-rule keys list \
  -g rg-ticketing --namespace-name sb-myticketzm-dev \
  --name RootManageSharedAccessKey --query primaryConnectionString -o tsv

# (b) Managed identity — assign RBAC roles to the app's identity
# Roles: "Azure Service Bus Data Sender" + "Azure Service Bus Data Receiver"
az role assignment create \
  --assignee <managed-identity-client-id> \
  --role "Azure Service Bus Data Sender" \
  --scope /subscriptions/<sub>/resourceGroups/rg-ticketing/providers/Microsoft.ServiceBus/namespaces/sb-myticketzm-dev
# repeat for "Azure Service Bus Data Receiver"

  3. Set the environment variables

    The services already read these (with empty defaults). Put them in docker-resources/.env.ticketing or your service's environment.

    # Option (a): connection string
AZURE_SERVICEBUS_CONNECTION_STRING=Endpoint=sb://sb-myticketzm-dev.servicebus.windows.net/;SharedAccessKeyName=RootManageSharedAccessKey;SharedAccessKey=...

# Option (b): managed identity (no secret)
AZURE_SERVICEBUS_NAMESPACE=sb-myticketzm-dev
AZURE_MANAGED_IDENTITY_ENABLED=true
AZURE_CLIENT_ID=<user-assigned-identity-client-id>   # if user-assigned

  4. Verify the binding is live

    Restart booking-service. The “namespace must be 6–50 chars” warning disappears, and you should see the Service Bus processor connect. Publish a catalog event and confirm booking-service's catalogEventConsumer receives it (check the booking-service subscription's active message count in the portal).

The app config in application.yml is already complete (retry, prefetch, checkpoint mode, topic entity type). You only supply credentials + the provisioned topics/subscriptions — no code changes required.

🐳 Option B — Local Azure Service Bus Emulator (recommended for dev)

Microsoft ships an official Service Bus emulator Docker image — run the real binder locally with no Azure subscription. It needs a companion SQL Server container for storage. Limits: 1 namespace, ≤50 topics/queues, ≤50 subscriptions/topic.

  1. Define the entities in servicebus-config.json

    Pre-declare the topics + the booking-service subscription (the emulator only creates what's in this file).

    // docker-resources/servicebus/config.json
{
  "UserConfig": {
    "Namespaces": [{
      "Name": "sbemulatorns",
      "Topics": [
        { "Name": "catalog-events",
          "Subscriptions": [{ "Name": "booking-service" }] },
        { "Name": "booking-events",  "Subscriptions": [] },
        { "Name": "identity-events", "Subscriptions": [] }
      ]
    }],
    "Logging": { "Type": "File" }
  }
}

  2. Add the emulator services to docker-compose

    servicebus-emulator:
  image: mcr.microsoft.com/azure-messaging/servicebus-emulator:latest
  ports: ["5672:5672"]
  environment:
    SQL_SERVER: sbemulator-mssql
    MSSQL_SA_PASSWORD: "${MSSQL_SA_PASSWORD}"
    ACCEPT_EULA: "Y"
  volumes:
    - ./servicebus/config.json:/ServiceBus_Emulator/ConfigFiles/Config.json
  depends_on: [sbemulator-mssql]

sbemulator-mssql:
  image: mcr.microsoft.com/mssql/server:2022-latest
  environment:
    ACCEPT_EULA: "Y"
    MSSQL_SA_PASSWORD: "${MSSQL_SA_PASSWORD}"   # 8+ chars, strong

  3. Point the services at the emulator

    The emulator uses a fixed connection string with the UseDevelopmentEmulator=true flag.

    AZURE_SERVICEBUS_CONNECTION_STRING=Endpoint=sb://localhost;SharedAccessKeyName=RootManageSharedAccessKey;SharedAccessKey=SAS_KEY_VALUE;UseDevelopmentEmulator=true;
The emulator now uses the default AMQP port 5672. RabbitMQ also uses 5672, so it was made opt-in (profile rabbitmq) and does not auto-start — it is not deleted and stays available for twende-ride. The two cannot run at once; start RabbitMQ (after stopping the emulator) with docker compose --profile rabbitmq up -d dev_rabbitmq.

Dev → Prod swap (no code changes)

# DEV (default): local profile -> emulator on 5672
# PROD: flip one env var -> managed identity + real namespace
export SPRING_PROFILES_ACTIVE=prod

Runtime note (Colima / Apple Silicon): SQL Edge needs real memory. The Colima VM was raised to 6 GiB / 4 CPU (colima start --cpu 4 --memory 6) — a 2 GiB VM OOM-kills SQL Edge and destabilises the stack.

🐰 Option C — Use the running RabbitMQ as the local binder

If you'd rather use the RabbitMQ you already have running instead of the emulator, swap the Spring Cloud Stream binder. This puts the idle broker to work. Best done with a Spring profile so production still uses Service Bus.

<!-- pom.xml: add alongside the servicebus binder -->
<dependency>
  <groupId>org.springframework.cloud</groupId>
  <artifactId>spring-cloud-stream-binder-rabbit</artifactId>
</dependency>
# application-local.yml  (activate with SPRING_PROFILES_ACTIVE=local)
spring:
  rabbitmq: { host: localhost, port: 5672, username: admin, password: admin_password }
  cloud:
    stream:
      default-binder: rabbit          # override 'servicebus'
      bindings:
        catalogEventConsumer-in-0: { destination: catalog-events, group: booking-service }
        ticketOutput-out-0:        { destination: booking-events }
With the rabbit binder, Service Bus “topics” map to RabbitMQ topic exchanges and consumer groups map to durable queues — the same StreamBridge / function code works unchanged. Keep servicebus as the default binder for the prod profile.

🧭 Recommendations

For local dev now: use Option B (emulator) or Option C (RabbitMQ binder + local profile). Both let cross-service events flow without an Azure subscription. Option C also gives the currently-idle RabbitMQ a real job.
For staging/production: use Option A with managed identity (roles: Azure Service Bus Data Sender + Data Receiver) and pull the connection string from Key Vault (AZURE_KEYVAULT_ENABLED=true). No secrets in env.
Decide RabbitMQ's fate: either adopt it as the local binder (Option C) or remove dev_rabbitmq from the ticketing compose stack so it isn't mistaken for an active dependency. Also fix the 5672 port clash before running the emulator alongside it.
Complete the topology: add explicit bindings + topics for the dynamic StreamBridge destinations (chargeback-events, notification, organization, userRole) and add subscribers for booking-events / identity-events, which are currently produced with no consumer.
